  컬럼이 이미 임의 문자열을 받게 설계돼 있어 기술적으로는 둘 다 지원 가능하지만, 실제 선택은
  1-7 착수 전에 필요하다.

## 스키마 / 설계

- **`jibun_address`/`road_address` 통합 저장이 충분한가.** 원본 API는 `jibun`/`bonbun`/
  `bubun`을 분리된 필드로 주는데, V1 스키마는 이를 합쳐서 하나의 문자열 컬럼으로 저장한다.
  지오코딩 입력으로는 합쳐진 주소가 적합하지만, 나중에 번지수를 다시 분해해서 써야 하는
  요구가 생기면 이 설계가 걸림돌이 될 수 있다. 의도한 설계인지, 1-5~1-7 진행하면서 재검토가
  필요한지 미정.
- **`ingest_status.raw_s3_key` 컬럼명과 현재 단계의 불일치.** 컬럼명은 S3 키를 전제하지만,
  1단계(1-6)는 S3가 아니라 로컬 파일로 원본을 저장한다. 지금 단계에서는 로컬 경로 문자열을
  그대로 넣을지, 컬럼명을 더 중립적인 이름으로 바꿀지, 아니면 2단계(S3 전환) 전까지는 그냥
  두고 갈지 결정되지 않았다.
- **`CHAR` → `VARCHAR` 전환 범위.** `sgg_code`는 4개 테이블 전부 `VARCHAR(5)`로 바꿨지만,
  같은 이유(Hibernate 기본 매핑과의 불일치 가능성)가 있는 `apt_trade.trade_key`(`CHAR(64)`)와
  `ingest_status.deal_ym`(`CHAR(6)`)은 범위에서 제외했다. 이 두 컬럼에 대응하는 엔티티를 만들
  때 같은 문제가 재발할지, 재발하면 같은 방식으로 고칠지 아직 정해지지 않았다.

## 성능 / 캐시

- **Redis 캐시 적용 대상 미정.** 3단계 과제로 미뤄져 있을 뿐, "어떤 조회를 캐싱할지"(지역
  목록처럼 자주 바뀌지 않는 데이터인지, 통계처럼 계산 비용이 큰 데이터인지)는 구체화된 바
  없다.

## 배치

- **`runDate` 누락 시 처리.** 지금은 Job이 시작된 뒤 NPE로 실패한다. 실제 수집 Job에서 시작 전
  파라미터 검증(`JobParametersValidator`)을 둘지 1-6에서 정한다. (Hy의 1-4 기록에서 옮김)
- **`trade_key` 생성 시 공백 처리 규칙.** `aptDong` 등은 값 없음이 공백 한 칸으로 온다. 해시 입력에
  trim을 일관되게 적용하지 않으면 같은 거래가 다른 키가 된다. 1-6 upsert 작성 전에 규칙을 정한다.
  (Hy의 1-5 기록에서 옮김)
- **`RestClient` 타임아웃 값.** 지금은 설정이 없다. 1-6에서 연결·읽기 타임아웃을 정한다.
  (Hy의 1-5 기록에서 옮김)

## 운영 환경 / 로컬 개발

- **로컬 포트 충돌이 반복되는 구조적 문제인지.** PostgreSQL(5432), API 서버(8080) 포트가 각각
  다른 사이드 프로젝트와 충돌한 적이 있다. 지금까지는 그때그때 해결했는데(한 번은 상대
  컨테이너를 내리고, 한 번은 이쪽 포트를 바꿈), 로컬 개발 환경 전체에 포트 규칙을 정해둘지,
  아니면 충돌할 때마다 개별 대응할지는 정해지지 않았다.
- **GitHub 저장소 공개 설정의 재확인 필요성.** 저장소는 현재 Public 상태다(생성 시 기본값으로
  만들어졌고, 공개 여부를 명시적으로 정한 적은 없다). 포트폴리오로 외부에 공유하기 전에, 민감한
  값이 커밋에 없는지 재점검하고 공개 상태를 유지할지 명시적으로 확정하는 절차가 필요하다.
