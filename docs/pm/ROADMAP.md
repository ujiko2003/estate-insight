# ROADMAP

> 신규 합류 PM을 위한 인계 문서. 목표, 마일스톤, 범위 경계를 정리한다.
> 마지막 갱신: 2026-11-09 (1단계 진행 중, 1-4 완료)

## 목표

국토교통부 아파트 매매 실거래가 공공데이터를 주기적으로 수집해 S3와 PostgreSQL+PostGIS에 쌓고,
지도 기반 검색·통계 API를 AWS에서 운영하는 서비스.

프로젝트의 목적은 백엔드 이직용 포트폴리오다. 평가 기준은 **기능의 개수가 아니라 "문제 → 선택 →
결과"가 코드와 문서로 남아있는지**다. 따라서 로드맵의 우선순위도 "기능을 더 넣는 것"보다
"이미 넣은 기능의 설계 근거와 성능/운영 수치를 기록으로 남기는 것"에 맞춰져 있다.

## 마일스톤

| 단계 | 범위 | 상태 |
|---|---|---|
| 1단계 — 로컬 MVP | 멀티모듈 뼈대, 로컬 인프라, 조회 API 4종, 배치 수집 파이프라인, 통합 테스트 | 진행 중 (1-1~1-4 완료, 다음 1-5) |
| 2단계 — AWS 배포 | Terraform(VPC/RDS/ECS/S3/ECR), GitHub Actions OIDC 배포, EventBridge 스케줄 배치 | 예정 |
| 3단계 — 확장 + 성능 | 전국·수년치 데이터 적재, 인덱스 튜닝, 파티셔닝, Redis 캐시, k6 부하 측정 | 예정 |
| 4단계 — 운영 + 고가용성 | CloudWatch 알람, Multi-AZ, 장애 훈련(AWS FIS), 포스트모템 | 예정 |

1단계 세부 진행 상황은 `BACKLOG.md`를 참조.

## 범위 — 하기로 한 것

- MVP 조회 기능 4종: 실거래 조건 검색, 지도 영역/반경 검색, 단지별 월 평균 가격 추이, 시군구 통계
- PostGIS 기반 공간 검색 (`GEOGRAPHY` 타입 + GIST 인덱스)
- Flyway로 전체 스키마를 버전 관리 (Hibernate `ddl-auto`는 자동 생성에 쓰지 않음)
- Spring Batch 기반 수집 파이프라인, 지역×계약월 단위로 분할 수집
- 로컬 개발 환경은 Docker Compose(PostgreSQL+PostGIS, Redis)로 통일
- GitHub 공개 저장소로 코드 관리 (`github.com/ujiko2003/estate-insight`, public)
- 시드 데이터는 서울 25개 자치구 전체를 테이블에 넣어두되, MVP 수집 대상은 강남구(11680) 1개 구만 활성화

## 범위 — 안 하기로 한 것 / 뒤로 미룬 것

- **NAT Gateway 미사용** — 비용 절감이 우선. 배포 구조는 이 제약을 전제로 설계한다.
- **RDS는 단일 AZ로 시작** — Multi-AZ 전환은 4단계(운영/고가용성) 과제.
- **Redis 캐시 로직은 3단계로 연기** — 1단계에서는 Redis 컨테이너만 로컬 환경에 올려두고, 실제 캐싱
  대상(어떤 조회를 캐싱할지)과 로직은 아직 정하지 않았다. 지금 두 모듈(`api`, `batch`) 어느 쪽에도
  Redis 클라이언트 의존성은 추가되어 있지 않다.
- **S3 적재는 2단계부터** — 1단계(1-6)에서는 수집 원본을 로컬 파일로만 저장하고, 2단계에서 S3로
  교체한다.
- **배치(`batch`) 모듈은 Flyway를 직접 실행하지 않는다** — 스키마 변경 권한을 `api` 모듈 하나로
  유지하기 위한 결정. 두 애플리케이션이 동시에 마이그레이션을 트리거하는 상황을 피한다.
- **전국·수년치 데이터 적재는 3단계** — 1단계는 서울 1개 구, 짧은 기간만 다룬다.
- **AWS Budgets 알람을 배포보다 먼저 설정** — 2단계 착수 조건.

## 개발 프로세스 — 코드 작성 주체 분리

이 프로젝트는 "개발자가 직접 작성하며 백엔드·DB·인프라 동작 원리를 익힌다"는 학습 목적을 겸한다.
그래서 코드 작성 주체가 영역별로 명확히 나뉘어 있다:

- **Gradle 빌드 관련 파일 전체** (모든 모듈의 `build.gradle.kts`, 루트 `settings.gradle.kts`,
  Gradle wrapper) — AI 어시스턴트가 작성/수정한다. 학습 목표가 Gradle DSL 문법이 아니라고 판단했고,
  실무에서도 이 보일러플레이트를 손으로 치는 경우가 드물기 때문이다. Boot 애플리케이션 모듈(`api`,
  `batch`)의 초기 보일러플레이트(기본 `@SpringBootApplication` 클래스 포함)는 Spring Initializr로
  생성한 뒤 멀티모듈 구조로 재배치한다.
- **그 외 전부** — 엔티티, 리포지토리, 컨트롤러, 쿼리, 배치 Step, `application.yml` 등 설정값,
  Flyway 마이그레이션 SQL — 개발자가 직접 작성한다. 어떤 의존성을 어떤 scope(`api`/`implementation`)
  로 선언할지 같은 설계 판단도 이 범위에 포함된다.
