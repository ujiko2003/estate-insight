# 1-6 수집 Step — 작업 브리프
작성: 2026-11-11

## 목표
활성 지역(강남구) × 계약월 단위로 실거래가를 받아 원본을 로컬 파일로 남기고, `apt_complex`·`apt_trade`에
중복 없이 적재하며, 어디까지 받았는지를 `ingest_status`에 기록한다.
1단계의 "수집 파이프라인"이 실제로 돌기 시작하는 단계이고, 1-7(지오코딩)과 1-8(조회 API)은 여기서 쌓인
데이터를 전제로 한다.

## 완료 조건 (DoD)
BACKLOG의 6개를 옮기고, 확인 방법을 명령·쿼리로 다듬은 안이다(BACKLOG 반영 여부는 Hy 확인).

| # | 작업 | 확인 방법 |
|---|---|---|
| 선행 1 | `umd_code` → `VARCHAR(5)` (V5) | `api` 기동 후 `information_schema.columns`에서 `character varying(5)` |
| 선행 2 | 테스트에서 Job 자동 실행 끄기 | `./gradlew :batch:test` 전후 `batch_job_execution` 행 수 동일 |
| 1 | Chunk Step 설계 | 더미 Reader/Writer로 Step이 COMPLETED, 읽은 건수 = 쓴 건수(`batch_step_execution`의 `read_count`, `write_count`) |
| 2 | 원본 로컬 파일 저장 | 실행 후 `지역/계약월` 단위 파일 생성, `ingest_status.raw_s3_key`에 그 경로 |
| 3 | upsert | 같은 `runDate` 범위를 두 번 수집(두 번째는 다른 `runDate`)해도 `apt_trade` 행 수 동일, `count(*) = count(distinct trade_key)` |
| 4 | `ingest_status` 갱신 | 성공 시 `DONE`과 `total_count = saved_count`, 실패(예: 잘못된 키) 시 `FAILED`와 `last_error` 기록 |

## 시작 전에 필요한 것
- 없음. 서비스키, 실제 응답 샘플(`gangnam-202609.xml`), 테스트 실행 방법은 1-5에서 준비됨.
- `initialize-schema: never` 적용 후 첫 `bootRun`이 정상 종료되는지 이번 작업 첫 실행 때 같이 확인.

## 먼저 내려야 할 결정

### 1. Chunk의 한 건(item)을 무엇으로 볼 것인가 — 가장 중요
- (A) **거래 1건**: Reader가 API 페이지를 넘기며 거래를 하나씩 읽음. Spring Batch 교과서적 형태지만,
  원본 파일 저장과 `ingest_status`가 "지역×월" 단위라서 Reader 안에 상태 관리가 섞인다.
- (B) **지역×계약월 1건**: Reader는 수집 대상(`ingest_status` 행)을 읽고, Processor가 API 호출·원본 저장·
  변환을 하고, Writer가 그 달 거래 전체를 upsert하고 상태를 `DONE`으로 바꾼다. chunk size 1이면
  "한 달 = 한 트랜잭션"이 되어 중단 후 재시작 단위와 수집 이력 단위가 일치한다.
- PM 의견: **(B)**. 강남구 한 달이 125건 수준이라 메모리 부담이 없고, BACKLOG의 "지역×계약월 단위로
  나눠 처리"와 테이블 설계(`ingest_status` PK)에 그대로 맞는다. 면접 질문 "왜 거래 단위가 아니냐"에
  답할 근거가 분명하다.

### 2. 어떤 계약월을 수집할 것인가
- (A) `runDate` 기준 최근 N개월(CLAUDE.md의 "최근 2~3개월 매일 재수집")을 자동 계산
- (B) `fromYm`, `toYm` 파라미터로 명시
- PM 의견: **(A), N=3**. 2단계 EventBridge 일일 실행과 그대로 이어지고, `runDate`가 JobInstance를
  정한다는 16번 결정과도 맞다. 수년치 적재(3단계)는 그때 (B)를 추가한다.

### 3. upsert를 무엇으로 쓸 것인가
- (A) JPA 엔티티 + `save` — 조회 후 insert/update, 건마다 SELECT가 붙고 `trade_key CHAR(64)` 매핑 문제
  (OPEN_QUESTIONS)도 다시 마주친다.
- (B) JDBC(`JdbcTemplate` 또는 `JdbcBatchItemWriter`) + `INSERT ... ON CONFLICT (trade_key) DO UPDATE`
- PM 의견: **(B)**. 한 문장으로 "없으면 넣고 있으면 갱신"이 DB 안에서 원자적으로 끝나고, 해제 표시가
  나중에 붙는 거래(`is_cancelled`)를 갱신하는 요구에 정확히 맞는다. `apt_complex`도 같은 방식으로
  `apt_seq` 기준 upsert를 먼저 한다(FK 때문에 단지가 먼저 있어야 함).

### 4. 한 거래의 변환이 실패하면
- (A) 그 지역×월 전체를 `FAILED`로 두고 `last_error` 기록(다음 실행에서 재시도)
- (B) 그 거래만 건너뛰고 나머지 저장, 건너뛴 수를 기록
- PM 의견: **(A)**. 14번 결정(이상값은 0으로 넣지 않는다)과 같은 방향이고, (B)는 `total_count`와
  `saved_count`가 어긋나는 원인을 따로 추적해야 한다. 실제 데이터에서 실패가 자주 나오면 그때 (B)로 바꾼다.

### 5. 기존 `logTestJob` 처리
Job 빈이 2개가 되면 Boot가 실행할 Job을 정하지 못해 `spring.batch.job.name`을 매번 넘겨야 한다.
- (A) `logTestJob` 삭제(1-4 증거는 커밋 이력과 DECISIONS 12·16번에 있음)
- (B) 유지하고 실행 때마다 Job 이름 지정
- PM 의견: **(A)**.

## 작업 순서 제안
1. **선행 2건** (1~1.5시간) — V5 마이그레이션, 테스트 설정. 확인: 위 표의 선행 1·2.
2. **Job 뼈대 + 대상 월 계산** (반나절) — 결정 1·2·5 반영. 첫 Step(Tasklet)에서 활성 지역×최근 3개월
   `ingest_status`를 `PENDING`으로 만들거나 되돌리고, 두 번째 Step은 더미 Processor/Writer로 Chunk 흐름만
   통과. 확인: DoD 1.
3. **변환 규칙 + 단위 테스트** (반나절) — `AptTradeFieldParser`에 날짜·면적·층·해제 여부·`trade_key` 추가.
   `gangnam-202609.xml` 125건 전부 변환되는지 테스트. 확인: `--tests 'com.hy.estate.batch.*'` 통과.
4. **원본 파일 저장** (1~2시간) — Processor에서 응답 원문을 파일로. 확인: DoD 2.
5. **upsert** (반나절) — 단지 → 거래 순서. 확인: DoD 3.
6. **상태 전이 + 실패 확인** (1~2시간) — `IN_PROGRESS`/`DONE`/`FAILED`. 확인: DoD 4.

실제 응답에서 확인한 변환 규칙(강남구 2026-09, 125건):
- `rgstDate`, `cdealDay`는 `26.09.30`처럼 **2자리 연도 `yy.MM.dd`**, 값이 없으면 공백 한 칸(등기 80건, 해제
  124건이 공백).
- `aptDong`은 125건 중 86건이 공백 한 칸 → `null`로 저장하고 `trade_key`에서도 같은 규칙.
- `cdealType`은 공백 또는 `O`(1건) → `is_cancelled`.
- `excluUseAr`는 `84.93` 같은 소수 → `NUMERIC(8,2)`, `floor`는 정수(지하층은 음수일 수 있음).
- `umdCd`는 5자리(`10600`) — 선행 1의 근거.

## 학습 포인트
코드는 전부 Hy가 작성한다. Gradle 의존성이 새로 필요하면 그 파일만 AI가 수정한다.
- **Chunk 지향 처리**: Reader/Processor/Writer의 책임 분리, chunk 단위 트랜잭션, 실패 시 어디서 다시
  시작하는지(`ExecutionContext`).
- **`INSERT ... ON CONFLICT DO UPDATE`**: PostgreSQL upsert, `EXCLUDED` 참조, 어떤 컬럼을 갱신 대상에서
  빼는지(`created_at`).
- **자연키 해시**: 무엇을 키에 넣고 무엇을 빼는가(해제 여부는 빼는 이유 — CLAUDE.md DB 설계).
- **Job 파라미터와 재실행**: 같은 계약월을 다른 `runDate`로 다시 받는 것이 왜 정상 동작인지.

## 포트폴리오 포인트
- "Chunk의 한 건을 지역×월로 잡은 이유" — 결정 1. 재시작 단위·트랜잭션 단위·이력 단위의 일치.
- "두 번 수집해도 행이 늘지 않는다" — upsert 전후 행 수를 수치로 남긴다.
- 해제 거래가 나중에 갱신되는 흐름 — `is_cancelled`가 `false → true`로 바뀌는 사례가 실제 재수집에서
  나오면 기록.
- 미리 남길 수치: 한 지역×월 처리 시간(1-5의 Step 224ms가 호출만의 기준선), 저장 건수, 재수집 시 갱신 건수.

## 리스크
- **일정**: DoD가 4개에서 6개로 늘었다. 기획서 일정(11/12~17, 평일 4일)보다 하루 정도 더 걸릴 수 있고,
  그러면 1-7이 밀린다. 11/30은 관리용 기준점이라 품질을 우선한다.
- **보안**: 원본 파일 저장 경로를 `.gitignore`에 먼저 추가한다. 응답 원문엔 키가 없지만, 수집 데이터가
  공개 레포에 쌓이면 안 된다. 실패 로그(`last_error`)에 요청 URL을 넣지 않는다(키 포함).
- **기술**: 결정 1에서 (B)를 고르면 Spring Batch 예제와 모양이 달라 레퍼런스가 적다. Boot 4/Batch 6의
  Chunk API 변경(패키지 이동 등)도 1-4처럼 실행으로 확인해야 한다.
- **API 한도**: 개발 계정 일일 호출 한도 안에서 충분하지만, 페이지 크기(`numOfRows`)를 실제 건수보다 크게
  잡아 호출 수를 줄인다(실제 응답은 200으로 받음).
