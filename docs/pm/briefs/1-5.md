# 1-5 실거래가 API 클라이언트 (남은 작업: 응답 파싱 + 금액 처리) — 작업 브리프
작성: 2026-11-11

## 목표
API 응답을 수집 Step이 바로 쓸 수 있는 값으로 바꾸고, 그 동작을 네트워크 없이 테스트로 보장한다.
1-6(수집 Step)은 이 파서와 금액 변환 위에 올라가므로, 여기서 잡지 못한 형식 문제는 DB 적재 단계에서
훨씬 늦게 드러난다.

현재 상태: 호출(`AptTradeApiClient`)과 XML 변환(`AptTradeXmlParser`)은 커밋됨, 실제 호출 DoD 완료
(2026-11-10). 남은 것은 금액 변환과 단위 테스트.

## 완료 조건 (DoD)
BACKLOG 원문: "쉼표 포함 금액, 공백 포함 금액 등 엣지 케이스 테스트 통과."
확인 가능한 형태로 다듬은 안(BACKLOG 반영 여부는 Hy 확인):

1. `./gradlew :batch:test --tests 'com.hy.estate.batch.client.*'` 통과 (전체 테스트는 아래 리스크 참고).
2. 금액 변환 테스트에 최소 다음 케이스가 있다.
   - `335,000` → 335000, `5,000` → 5000, `900` → 900
   - 앞뒤 공백 `"  82,500 "` → 82500
   - 빈 문자열, 공백만, `null`, 숫자가 아닌 값 → 아래 결정 1에 따른 동작
3. 파서 테스트에 최소 다음 케이스가 있다.
   - 실제 응답 파일(강남구 2026-09) → `totalCount` 125, 요청한 `numOfRows`만큼 `items`
   - `item` 1건 응답 → `items.size() == 1` (리스트로 읽히는지)
   - 거래 0건 응답 → 빈 목록
   - `resultCode` 오류, 접근거부(`OpenAPI_ServiceResponse`) → `IllegalStateException`
4. 커밋된 테스트 리소스 파일에 서비스키가 없다 (`git grep -i servicekey -- batch/src/test` 결과 없음).

## 시작 전에 필요한 것
- 거래 0건 달의 **실제 응답**: 아직 확인 안 됨(Hy 기록 "남은 문제"). 아직 오지 않은 계약월 등으로 1회
  호출해 원문을 저장해 두면 0건 케이스를 추측이 아니라 실제 모양으로 테스트할 수 있다.
- 그 외 없음. 테스트 의존성(JUnit, AssertJ)은 이미 `batch` 테스트 클래스패스에 있어 Gradle 수정 불필요.

## 먼저 내려야 할 결정

**2026-11-11 Hy 결정 (`DECISIONS.md` 14번)**
- 금액이 `null`이거나 0 이하면 `IllegalArgumentException`을 던진다.
  빈 문자열·숫자 아님·`int` 범위 초과는 `Integer.parseInt`의 `NumberFormatException`(IAE의 하위
  클래스)로 같은 계열이 된다 — 테스트에서 이 케이스들도 IAE로 검증할 것.
- 변환은 별도 클래스로 분리해, 이후 날짜·면적 등 변환 메서드를 한곳에 모은다.
- 테스트용 XML은 전부 `src/test/resources`에 보관한다. 직접 만든 파일(1건, 오류, 접근거부)과 실제
  응답 파일은 파일명으로 구분해 두면 나중에 헷갈리지 않는다.

아래는 결정 전 검토한 선택지(기록용).

### 1. 금액이 비었거나 숫자가 아닐 때
- (A) 예외를 던진다 — 형식 이상이 즉시 드러난다. 한 건 때문에 Step이 멈출 수 있지만, 건너뛸지는
  1-6에서 Chunk의 skip 정책으로 따로 정할 수 있다.
- (B) `null`을 반환하고 호출하는 쪽이 판단 — 유연하지만 `deal_amount`가 `NOT NULL`이라 결국 1-6에서
  다시 처리해야 한다.
- (C) 0으로 바꾼다 — 적재는 되지만 평균가·통계가 조용히 틀어진다.
- PM 의견: **(A)**. Hy가 1-5 기록 4번에서 고른 "수집이 조용히 비어 버리는 상황을 막는다"는 원칙과도
  맞는다. 정하면 커밋 메시지에 `결정:` 줄로 남긴다.

### 2. 금액 변환을 어디에 둘 것인가
- (A) `AptTradeXmlParser`가 변환까지 해서 숫자 필드를 가진 결과를 반환
- (B) 별도의 작은 변환 메서드/클래스로 분리, 파서는 지금처럼 `String`을 유지
- (C) `Item` record 안에 `dealAmountAsInt()` 같은 메서드 추가
- PM 의견: **(B) 또는 (C)**. Hy 기록 3번("전부 `String`으로 받아 원본을 유지하고 변환 규칙을 한곳에
  모은다")과 맞고, 금액 테스트가 XML 없이 단독으로 돌아간다. 1-6에서 `dealYear/Month/Day` →
  `deal_date`, 면적 등 변환이 늘어날 것을 생각하면 (B)가 확장하기 쉽다.

### 3. 테스트용 XML을 어디에 둘 것인가
- (A) `batch/src/test/resources`에 실제 응답 파일로 저장
- (B) 테스트 코드 안에 텍스트 블록(`"""`)으로 작성
- PM 의견: **둘 다**. 실제 응답(정상, 0건)은 (A)로 원문 그대로, 1건·오류 같은 작은 케이스는 (B).
  실제 응답 파일은 공개 레포에 올라가므로 키가 없는지 확인 후 커밋.

## 학습 포인트
전부 Hy가 직접 작성한다(테스트 코드 포함). Gradle 파일은 수정이 필요 없다.
- **Jackson XML의 컬렉션 처리**: `useWrapping = false`로 반복 요소를 리스트로 읽는 방식, 요소가 1개일 때도
  리스트가 되는지.
- **단위 테스트 경계**: 네트워크·Spring 컨텍스트 없이 순수 객체만으로 테스트하는 범위를 정하는 것.
  `@SpringBootTest`가 아닌 일반 JUnit 테스트로 쓰는 이유.
- **파라미터화 테스트**: `@ParameterizedTest` + `@CsvSource`/`@NullAndEmptySource`로 엣지 케이스를
  표처럼 나열하는 방법.

  넘겨도 1-5 DoD에는 영향이 없다.
- **기술**: 0건 응답의 실제 모양 미확인(1단계에서 해소).
