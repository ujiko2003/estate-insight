# 1-6 ④ 원본 로컬 파일 저장 (실제 Reader·API 호출 포함) — 작업 브리프
작성: 2026-11-19 (상위 브리프: `briefs/1-6.md` 작업 순서 4단계)

## 목표
수집 Job이 처음으로 실제 API를 호출한다. 대상 월마다 응답 원문을 파일로 남기고, 그 위치를
`ingest_status.raw_s3_key`에 기록한다.

원본이 남아 있으면 세 가지가 가능해진다.
- 변환이나 upsert가 실패해도 API를 다시 부르지 않고 원인을 볼 수 있다.
- 2단계에서는 같은 파일이 S3로 옮겨간다.

**범위 주의**: 지금 `collectStep`은 더미 Reader(`ListItemReader`)와 출력만 하는 Writer로 되어 있다. 원본을 저장하려면 이번 작업에 다음이 함께 들어가야 한다.
- 진짜 Reader: 28번 결정에 따라 이번 `runDate`의 대상 월만 읽는다.
- Processor의 API 호출

변환과 upsert는 5단계, 상태 전이는 6단계다. 이번 작업에서 Writer는 `raw_s3_key`만 기록한다.

### 1. `raw_s3_key`에 무엇을 넣을까 (OPEN_QUESTIONS)
- (A) 컬럼 이름은 그대로 두고 **기준 디렉터리를 뺀 상대 경로**를 넣는다
  - 예: `apt-trade/sgg=11680/deal_ym=202609/run_date=2026-11-19/`
  - 기준 디렉터리는 설정값(`collect.raw-dir`)으로 둔다.
  - 2단계에서는 이 값이 그대로 S3 객체 키가 되고 기준만 버킷으로 바뀐다. 컬럼 이름과 실제 의미가 2단계에서 맞아진다.
- (B) V6로 컬럼 이름을 `raw_uri`로 바꾸고 `file:///…` → `s3://…` 형태로 넣는다
  - 의미는 정확하지만, 마이그레이션이 하나 늘고 절대 경로가 들어가 환경마다 값이 달라진다.
- (C) 로컬 절대 경로를 그대로 넣는다
  - 가장 쉽지만, 2단계에서 값의 형식이 바뀐다.
- PM 의견: **(A)**.

### 2. 같은 달을 다시 받으면 파일을 어떻게 할까
매일 최근 3개월을 다시 받으므로(23번), 같은 달 원본이 매일 생긴다.
- (A) 덮어쓴다: `sgg=11680/deal_ym=202609.xml`
  - 단순하지만, 해제 표시가 언제 붙었는지 같은 변화 이력이 사라진다.
- (B) **실행별로 보존**: `…/deal_ym=202609/run_date=2026-11-19/page-001.xml`
  - 하루에 약 100KB × 3개월로 용량이 작다.
  - `key=value` 형식의 경로라서 2단계 S3와 Athena에서 바로 파티션으로 쓸 수 있다.
  - 1-6 브리프의 포트폴리오 포인트("해제 거래가 `false → true`로 바뀌는 사례")를 원본으로 증명할 수 있다.
- PM 의견: **(B)**. 같은 `runDate`로 다시 실행하면 덮어쓴다. 같은 `runDate`의 재실행은 실패한 실행의 재시작뿐이므로 문제가 없다.

### 3. Reader가 대상 월 목록을 어떻게 얻을까 (28번에서 "구현 방식은 Hy가 확정"으로 남긴 부분)
- (A) `prepareTargetsStep`이 Job `ExecutionContext`에 목록을 넣고, `@StepScope` Reader가 꺼낸다
  - Spring Batch의 Step 간 데이터 전달을 배울 수 있다.
  - 목록이 `BATCH_JOB_EXECUTION_CONTEXT`에 직렬화되어 저장되고, 재시작할 때도 같은 목록을 쓴다.
- (B) 대상 월 계산을 별도 클래스로 빼고, Tasklet과 Reader가 둘 다 `runDate`와 설정으로 같은 계산을 한다
  - 단순하고 단위 테스트가 쉽다.
  - 두 Step 사이에 활성 지역이 바뀌면 결과가 어긋날 수 있다. 다만 실제로 일어날 가능성은 거의 없다.
- PM 의견: **(A)**. 28번에서 이미 권장한 방향이고, "Step 간 데이터를 어떻게 넘기나"는 Spring Batch 면접 단골 질문이다. 목록은 3건 규모라 직렬화 부담이 없다.
  - 단, 프로모션 리스너(`ExecutionContextPromotionListener`)와 직접 Job 컨텍스트에 쓰는 방법의 차이를 이해하고 고른다.

### 4. 원본을 언제 저장할까
- (A) **응답을 받자마자, 파싱하기 전에** 저장
  - 파싱이나 변환이 실패해도 원본이 남는다. 실패 원인을 보는 게 원본 저장의 목적이다.
- (B) 파싱과 검증이 성공한 뒤 저장
  - 정상 데이터만 남지만, 정작 디버깅이 필요한 실패 응답이 사라진다.
- PM 의견: **(A)**.
  - `resultCode` 오류 응답도 그대로 저장된다. 접근 거부(20번)처럼 XML이 아닌 응답도 저장할지는 함께 정한다. PM 의견은 저장이다.

## 작업 순서 제안
1. **결정 1~4 + `.gitignore`** (20분)
   - 확인: `git check-ignore -v <원본 디렉터리>/x`가 규칙을 출력한다.
2. **진짜 Reader** (1~1.5시간)
   - 결정 3대로 대상 월 목록(`sggCode`, `dealYm`)을 넘기고, 더미 `ListItemReader`를 교체한다.
   - Processor와 Writer는 아직 더미로 둔다.
   - 확인: `runDate=2026-11-19` 실행에서 read 3 / write 3, 로그에 202609~202611.
3. **Processor: API 호출 + 원본 저장** (1~1.5시간)
   - 페이지를 돌며 `fetchPage`를 호출한다(강남구는 한 달에 1페이지).
   - 응답을 받으면 바로 파일로 쓴다(결정 4). 파일 쓰기는 별도 클래스(예: `RawResponseStore`)로 둔다. 2단계에서 S3 구현으로 바꾸기 위해서다.
   - 확인: DoD 2·5·6.
4. **Writer: `raw_s3_key` 기록** (30분)
   - JDBC `UPDATE`, 상태(`status`)는 건드리지 않는다(6단계).
   - 확인: DoD 3, 다른 `runDate`로 실행해 DoD 4.
5. **테스트 + 커밋** (30분)
   - 파일 저장 클래스는 `@TempDir`로 단위 테스트한다.
   - 확인: DoD 7. 커밋 메시지에 "결정:" 줄을 넣는다.

합계 4~5시간. 하루 분량이고, 길어지면 4~5번째 단계를 다음 날로 넘긴다.

## 학습 포인트
코드는 전부 Hy가 작성한다. `collect.raw-dir` 같은 `application.yml` 설정값도 Hy가 쓴다.
- **Step 간 데이터 전달**: Job과 Step의 `ExecutionContext` 범위 차이, `@StepScope`와 지연 바인딩(`#{jobExecutionContext[...]}`), 재시작할 때 컨텍스트가 복원되는 원리.
- **Processor의 역할 경계**
  - Chunk 트랜잭션 안에서 외부 I/O(API 호출, 파일 쓰기)를 하면, 롤백되어도 파일은 남는다.
  - 결정 4가 이를 오히려 의도로 쓰는 이유를 설명할 수 있어야 한다.
- **저장소 추상화**: 인터페이스 하나에 로컬 구현을 두고, 2단계에서 S3 구현으로 바꾼다. 무엇을 인터페이스로 빼고 무엇을 빼지 않는지 판단한다.
- **`Files.createDirectories`, `Files.writeString`**: 경로 조립은 `Path.resolve`로 하고, 문자열 연결로 하지 않는 이유.

## 포트폴리오 포인트
- **문제 → 선택 → 결과**
  - 문제: 매일 같은 달을 다시 받는다.
  - 선택: 실행별로 원본을 보존하고 `key=value` 형식의 경로를 쓴다(결정 2).
  - 결과: 2단계에서 경로를 그대로 S3와 Athena 파티션으로 쓴다. 해제 거래 변화를 원본으로 추적할 수 있다.
- **'전' 측정(지금 남겨 둘 것)**: 한 지역×월의 API 호출 시간과 파일 저장 시간(`batch_step_execution`의 Step 시간). 1-5의 호출만 한 기준선은 224ms였다. 5단계 upsert를 붙인 뒤 비교한다.
- 하루 원본 용량(파일 크기 합계). 3단계 전국 적재의 저장 비용 추정에 쓴다.

## 리스크
- **보안**
  - `.gitignore`를 첫 실행 전에 추가한다.
  - 요청 URI에 서비스키가 들어 있으므로 로그에 URI를 남기지 않는다.
  - 파일 이름이나 경로에도 요청 파라미터를 그대로 쓰지 않는다.
- **테스트 오염**
  - `BatchApplicationTests`는 Job 자동 실행을 껐다(선행 2). 하지만 새로 만드는 Reader나 Processor 빈이 컨텍스트 로딩 중에 API를 부르지 않게 한다.
  - DoD 7에서 테스트 전후로 원본 디렉터리에 새 파일이 없는지 확인한다.
- **API 한도**: 실행 한 번에 3회 호출이고, 개발 중 여러 번 실행해도 개발 계정 한도 안이다.
- **타임아웃**
  - 실제 호출이 처음 Job 안으로 들어온다. `RestClient` 타임아웃(OPEN_QUESTIONS)이 없으면 응답이 멈췄을 때 Job이 끝나지 않는다.
  - 6단계까지 미뤄도 되지만, 개발 중에 멈추면 이 문제라는 것을 알아 둔다.
- **일정**: 범위가 BACKLOG 문구("파일 저장")보다 크다(Reader, API 호출 포함). 하루를 넘길 수 있다.
