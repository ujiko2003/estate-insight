# 1-6 ③ 변환 규칙 + 단위 테스트 — 작업 브리프
작성: 2026-11-17 (상위 브리프: `briefs/1-6.md`의 작업 순서 3단계)

## 목표
API 응답 `Item`(전부 문자열)을 DB에 넣을 수 있는 값(날짜, 숫자, boolean, `trade_key`)으로 바꾸는 규칙을 만들고
실제 응답 125건으로 검증한다. 다음 단계인 원본 저장, upsert, 상태 전이는 모두 이 변환 결과를 전제로 한다.
특히 `trade_key`는 upsert의 기준이라, 여기서 규칙이 흔들리면 "두 번 수집해도 행이 늘지 않는다"(DoD 3)가 깨진다.

## 완료 조건 (DoD)

## 먼저 내려야 할 결정

**결정 현황(2026-11-17, Hy)**: 1 → (B) DECISIONS 29, 2 → (B) 30, 3 → (A) 31. 전부 PM 의견 채택.

### 1. `trade_key`를 무엇으로 만들까 (OPEN_QUESTIONS "공백 처리 규칙")
들어갈 필드는 CLAUDE.md에서 확정됐다: 단지(`aptSeq`), 계약일, 층, 면적, 금액, 동. 해제 여부는 넣지 않는다.
- (A) **원본 문자열**을 strip해서 이어 붙여 해시
  - 단순하다.
  - 대신 표기가 바뀌면 키가 바뀐다. 실제 응답에 `60`과 `84.93`이 섞여 있어서, 같은 면적이 `60`과 `60.00`으로 오면 다른 거래가 된다. 금액 쉼표도 같은 문제다.
- (B) **변환한 값을 정해진 형식으로** 이어 붙여 해시
  - 형식: 계약일 ISO(`2026-09-30`), 면적 scale 2 문자열(`60.00`), 금액 정수, 층 정수, 동은 null이면 `""`.
  - 구분자 `|`로 이어 SHA-256 → 소문자 hex 64자.
  - 표기 차이에 흔들리지 않는다. 키 규칙이 변환 규칙 위에 서므로 한 곳만 맞추면 된다.
- PM 의견: **(B)**.
  - 구분자는 꼭 넣는다. 없으면 층 `1` + 면적 `12.00`과 층 `11` + 면적 `2.00`처럼 이어 붙인 결과가 같아질 수 있다.
  - null과 공백이 모두 `""`가 되는지 테스트로 고정한다.

### 2. 변환 결과를 어떤 모양으로 둘까
- (A) 거래 하나에 단지 필드까지 담은 record 하나
  - 단순하다.
  - Writer가 단지를 따로 골라 upsert해야 한다. FK 때문에 단지를 먼저 넣어야 하고, 125건에 단지가 80개다.
- (B) **단지 record + 거래 record** 두 개로 나눔
  - Item 하나에서 둘 다 만든다.
  - Writer가 단지는 `aptSeq` 중복을 제거해 먼저 upsert하고, 다음에 거래를 upsert한다. 테이블 두 개와 그대로 맞는다.
- PM 의견: **(B)**. 클래스 위치는 14번 결정대로 필드 단위 변환은 `AptTradeFieldParser`에 두고, Item을 record로 조립하는 클래스를 따로 둔다.

### 3. 단지 주소 컬럼(`jibun_address`, `road_address`) 형식
원본: `umdNm=대치동`, `jibun=1014-3`, `roadNm=도곡로78길`, `roadNmBonbun=00022`, `roadNmBubun=00000`.
- (A) 응답만으로 조립: `대치동 1014-3`, `도곡로78길 22`
  - 0 제거, 부번이 0이면 생략.
  - 변환기가 DB 없이 테스트된다. 시·도와 시군구 이름은 1-7 지오코딩 때 `region`과 합친다.
- (B) 전체 주소: `서울특별시 강남구 대치동 1014-3`
  - 지오코딩에 바로 쓸 수 있다.
  - 대신 변환 중에 `region`을 조회해야 해서 단위 테스트에 DB나 목이 필요하다.
- PM 의견: **(A)**. OPEN_QUESTIONS "주소 통합 저장" 항목도 이 결정으로 함께 정리한다.
- 오늘 정하기 어려우면 주소 조립만 5단계(upsert)로 미뤄도 된다.

## 작업 순서 제안
1. **결정 1~3** (15분): 정하면 커밋 "결정:" 줄로 남긴다.
2. **필드 변환 + 테스트** (1~1.5시간)
   - 계약일 조립, `yy.MM.dd` 날짜, 면적, 층, 해제 여부, 공백→null.
   - 확인: 필드 규칙 표의 엣지 케이스 테스트 통과.
3. **`trade_key` 생성 + 테스트** (1시간)
   - 확인 1: 동이 null인 경우와 `" "`인 경우 키가 같다.
   - 확인 2: 면적 `60`과 `60.00`의 키가 같다.
   - 확인 3: 층만 다르면 키가 다르다.
   - 확인 4: 길이가 64자다.
4. **Item → 단지·거래 record 변환 + 실제 응답 테스트** (1시간)
   - 확인: DoD 2·3의 수치(125, 80, 86, 45, 해제 1건).
5. **커밋 → PM 검증**
   - 커밋 메시지에 "결정:" 줄과 테스트 건수를 적는다.

합계 3.5~4시간. 오늘 하루에 끝나는 크기다.

## 학습 포인트
코드는 전부 Hy가 작성한다(CLAUDE.md). PM과 AI는 리뷰와 힌트만 준다.
- **`DateTimeFormatter`의 `yy`**
  - 두 자리 연도는 2000~2099로 해석된다. `uu`와 `yy`의 차이, `ResolverStyle.STRICT`에서 `yy`를 쓰면 생기는 문제를 확인한다.
  - `26.13.01`, `26.02.30`이 거부되는지 테스트로 확인한다.
- **`BigDecimal`의 `equals`와 `compareTo`**
  - `new BigDecimal("60").equals(new BigDecimal("60.00"))`는 false다. 결정 1(B)가 필요한 이유다.
  - `setScale(2)`와 `toPlainString()`의 역할을 이해한다.
- **SHA-256과 hex 변환**
  - `MessageDigest`, `HexFormat`(Java 17+), 문자열을 바이트로 바꿀 때 UTF-8을 명시하는 이유(단지명·동에 한글).
- **자연키 설계**
  - 무엇을 넣고 무엇을 빼는가(해제 여부). 정규화를 키 생성 앞에 두는 이유.

## 포트폴리오 포인트
- **문제 → 선택 → 결과**
  - 문제: API에 거래 ID가 없고 값 없음이 공백 한 칸, 면적 표기가 제각각이다.
  - 선택: 변환한 값을 정규화해서 해시한다(결정 1).
  - 결과: 실제 125건에서 서로 다른 키 125개. 표기만 다른 입력은 같은 키가 된다(테스트로 고정).
- **미리 남길 수치** (upsert의 '전' 기준): 125건, 단지 80, 해제 1, 동 공백 86, 등기 45.
  - 5단계 upsert에서 "두 번 수집 후에도 125행"을 비교할 기준이 된다.
  - 수집 전 `apt_trade` 행 수(현재 0 예상)도 5단계 시작 때 기록한다.

## 리스크
- **일정**
  - 이 단계는 BACKLOG DoD가 아니라 진행률이 오르지 않는다. 1-6의 DoD 3개는 4~6단계에 있다.
  - 오늘 안에 끝내야 이번 주에 1-6을 닫을 수 있다.
- **기술**

  - 테스트에 엣지 케이스를 직접 넣어 미리 막는다.
