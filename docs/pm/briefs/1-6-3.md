### 1. `trade_key`를 무엇으로 만들까 (OPEN_QUESTIONS "공백 처리 규칙")
들어갈 필드는 CLAUDE.md에서 확정됐다: 단지(`aptSeq`), 계약일, 층, 면적, 금액, 동. 해제 여부는 넣지 않는다.
- (A) **원본 문자열**을 strip해서 이어 붙여 해시
  - 단순하다.
  - 대신 표기가 바뀌면 키가 바뀐다. 실제 응답에 `60`과 `84.93`이 섞여 있어서, 같은 면적이 `60`과 `60.00`으로 오면 다른 거래가 된다. 금액 쉼표도 같은 문제다.
- (B) **변환한 값을 정해진 형식으로** 이어 붙여 해시
  - 형식: 계약일 ISO(`2026-09-30`), 면적 scale 2 문자열(`60.00`), 금액 정수, 층 정수, 동은 null이면 `""`.
  - 구분자 `|`로 이어 SHA-256 → 소문자 hex 64자.
  - 표기 차이에 흔들리지 않는다. 키 규칙이 변환 규칙 위에 서므로 한 곳만 맞추면 된다.
- PM 의견: **(B)**.
  - 구분자는 꼭 넣는다. 없으면 층 `1` + 면적 `12.00`과 층 `11` + 면적 `2.00`처럼 이어 붙인 결과가 같아질 수 있다.
  - null과 공백이 모두 `""`가 되는지 테스트로 고정한다.

### 2. 변환 결과를 어떤 모양으로 둘까
- (A) 거래 하나에 단지 필드까지 담은 record 하나
  - 단순하다.
  - Writer가 단지를 따로 골라 upsert해야 한다. FK 때문에 단지를 먼저 넣어야 하고, 125건에 단지가 80개다.
- (B) **단지 record + 거래 record** 두 개로 나눔
  - Item 하나에서 둘 다 만든다.
  - Writer가 단지는 `aptSeq` 중복을 제거해 먼저 upsert하고, 다음에 거래를 upsert한다. 테이블 두 개와 그대로 맞는다.
- PM 의견: **(B)**. 클래스 위치는 14번 결정대로 필드 단위 변환은 `AptTradeFieldParser`에 두고, Item을 record로 조립하는 클래스를 따로 둔다.

## 학습 포인트
코드는 전부 Hy가 작성한다(CLAUDE.md). PM과 AI는 리뷰와 힌트만 준다.
- **`DateTimeFormatter`의 `yy`**
  - 두 자리 연도는 2000~2099로 해석된다. `uu`와 `yy`의 차이, `ResolverStyle.STRICT`에서 `yy`를 쓰면 생기는 문제를 확인한다.
  - `26.13.01`, `26.02.30`이 거부되는지 테스트로 확인한다.
- **`BigDecimal`의 `equals`와 `compareTo`**
  - `new BigDecimal("60").equals(new BigDecimal("60.00"))`는 false다. 결정 1(B)가 필요한 이유다.
  - `setScale(2)`와 `toPlainString()`의 역할을 이해한다.
- **SHA-256과 hex 변환**
  - `MessageDigest`, `HexFormat`(Java 17+), 문자열을 바이트로 바꿀 때 UTF-8을 명시하는 이유(단지명·동에 한글).
- **자연키 설계**
  - 무엇을 넣고 무엇을 빼는가(해제 여부). 정규화를 키 생성 앞에 두는 이유.

## 학습 포인트
코드는 Hy가 작성한다.
- **`MessageDigest`는 스레드 안전하지 않다.**
  - 호출할 때마다 `getInstance("SHA-256")`로 새로 만든다. static 필드로 공유하면 안 된다.
  - 다음 단계에서 chunk가 병렬로 돌면 문제가 된다.
- **`NoSuchAlgorithmException`은 checked 예외다.**
  - SHA-256은 모든 Java 플랫폼이 반드시 지원한다(Java SE 명세). 그래서 이 예외는 사실상 발생하지 않는다.
  - 이런 예외를 `IllegalStateException`으로 감싸는 이유를 설명할 수 있어야 한다.
- **`getBytes(StandardCharsets.UTF_8)` 명시**
  - 생략하면 OS 기본 인코딩을 따른다.
  - 동 이름에 한글(`동일파크스위트`)이 있어서, 로컬 macOS와 2단계 ECS 컨테이너에서 키가 달라질 위험이 있다.
- **고정값 테스트의 의미**
  - 성질 테스트(같다, 다르다)만으로는 형식 변경을 잡지 못한다. 순서를 바꾸거나 구분자를 바꿔도 통과한다.
  - 고정값 테스트가 있어야 "키 형식은 바꾸면 안 되는 계약"이 된다.
